# sx1262-linux

Внешний модуль Linux 6.12 для **LoRa PHY SX1262**. До восьми независимых
радио, в том числе на одной SPI-шине, с отдельными или объединёнными через
OR прерываниями. GPIO задаются через Device Tree, включая GPIO расширителей
TCA9554. Привязки к Orange Pi или Allwinner в драйвере нет.

Reticulum/RNode/LoRaWAN, фрагментация, адресация, повторные передачи и политика
доступа к эфиру в драйвер не входят. Программа передаёт и получает исходные
LoRa payload. CAD, FSK и энергосберегающие режимы в этой версии не реализованы.

## Сборка

Из каталога проекта, с уже собранным ядром и его `Module.symvers`:

```sh
make KDIR=/absolute/path/to/linux-build \
    ARCH=arm CROSS_COMPILE=/absolute/path/to/host/bin/arm-buildroot-linux-gnueabihf- W=1
```

Результат — `sx1262.ko`. Для этой рабочей копии:

```sh
make KDIR="$PWD/../RNS-Gate/Firmware/system/output_gate-2026.08/build/linux-6.12.3" \
    ARCH=arm \
    CROSS_COMPILE="$PWD/../RNS-Gate/Firmware/system/output_gate-2026.08/host/bin/arm-buildroot-linux-gnueabihf-" W=1
```

Нужны `CONFIG_MODULES=y`, `CONFIG_SPI=y`, `CONFIG_GPIOLIB=y`, драйверы SPI,
GPIO и interrupt controller целевой платформы. Для TCA9554 нужны I²C и
`CONFIG_GPIO_PCA953X=y/m`. На одном chip select не должно одновременно быть
узлов spidev и sx1262.

Установка внешнего модуля стандартная: `make ... modules_install` с нужным
`INSTALL_MOD_PATH`, затем `depmod` для установленного ядра. Device Tree должен
быть установлен отдельно. Устройства `/dev/sx1262N` создаются через miscdevice,
права по умолчанию `0600`. Номер соответствует порядку probe; постоянные имена
можно назначить через udev по родительскому SPI-устройству.

## Buildroot

`buildroot/` — самостоятельное дерево BR2_EXTERNAL. Добавить его **к существующему**
списку внешних деревьев, включить `BR2_PACKAGE_SX1262_LINUX=y`, затем собрать
цель `sx1262-linux`:

```sh
make -C /path/to/buildroot O=/path/to/output \
    BR2_EXTERNAL="/path/to/existing-external /path/to/sx1262-linux/buildroot" menuconfig
make -C /path/to/output sx1262-linux
```

Пакет использует стандартный `kernel-module`, устанавливает модуль в target,
а UAPI-заголовок — в staging. После изменения локальных исходников используется
`sx1262-linux-rebuild`. Пакет не меняет DTS и конфигурацию ядра автоматически.
Тестовая утилита не устанавливается в target этим пакетом.

## Подключение и DT

Описание свойств: `Documentation/devicetree/bindings/net/semtech,sx1262.yaml`.
Шаблон двух плат LoraMulti: `examples/loramulti.dtsi`. Он требует определить
метки `lora_spi`, `lora_i2c` и `LORA_IRQ_SPEC` в DTS конкретной платы.

| Сигнал LoraMulti | Подключение |
| --- | --- |
| NSS | TCA9554 P5, через `cs-gpios` SPI-контроллера |
| NRST | P6, `reset-gpios`, active low |
| BUSY | P7, `busy-gpios`, active high |
| DIO1 до диода | P4, необязательный `dio1-gpios` |
| RXEN / TXEN | P2 / P1, `rxen-gpios` / `txen-gpios` |
| DIO_INT после OR | общий IRQ SoC, **level high** |

Для восьми модулей добавить расширители с уникальными адресами `0x20..0x27`,
восемь элементов `cs-gpios` и восемь SPI-узлов с `reg = <0>.. <7>`.
Реальные адреса определяются перемычками A0..A2. Число аппаратных NSS у SoC
не ограничивает число GPIO CS, если SPI-контроллер поддерживает их стандартным
способом. Встроенный драйвер TCA9554 обслуживает расширитель; радиодрайвер не
обращается к I²C напрямую.

У всех участников OR должен быть один IRQ с одинаковым типом. У каждого свой
threaded handler (`SHARED | ONESHOT`), собственные блокировки и состояние.
Опциональный P4 позволяет отсеять IRQ соседнего радио без обращения к SPI.
Если P4 не описан, драйвер читает IRQ-регистр каждого радио. DIO1 самого чипа
сбрасывается подтверждением флагов через SPI. Прерывание расширителя TCA9554
для этой схемы не требуется.

Для отдельного DIO1 допускается rising-edge IRQ. Для OR использовать level-high:
событие второго радио может возникнуть, пока первое уже удерживает общую линию.
Свойство `dio1-gpios` не нужно дублировать на том же физическом GPIO, который
уже используется как IRQ; оно предназначено для отдельного входа до OR.

## RF-профили

`semtech,sx1262`: кварц, LDO, мощность чипа −9..22 dBm. Аппаратный диапазон
по умолчанию 150..960 MHz; **диапазон конкретного модуля с его согласованием
нужно ограничить** через `semtech,frequency-min-hz` / `frequency-max-hz`.

`"ebyte,e22-x00m30s", "semtech,sx1262"`: общие границы профиля 410..930 MHz, TCXO 1.8 V,
DC-DC, диапазон выходной мощности 8..30 dBm. Таблица по умолчанию сохраняет
преобразование из rsReticulum-sx1262: chip power = output power − 17;
OCP = 0x18 до 22 dBm включительно, затем 0x38. Это исходная настройка для
проверки на железе, а не измеренная здесь калибровка мощности.

Общие границы профиля не означают, что один модуль работает во всём диапазоне.
Для E22-400M30S задать в его DTS-узле:

```dts
compatible = "ebyte,e22-x00m30s", "semtech,sx1262";
semtech,frequency-min-hz = <410000000>;
semtech,frequency-max-hz = <493000000>;
```

Диапазон 410..493 MHz указан в [спецификации Ebyte](https://www.cdebyte.com/products/E22-400M30S).
Производитель указывает для этого варианта SX1268; работу общего RF-профиля
и последовательности инициализации на нём необходимо подтвердить на стенде.
Для высокочастотного варианта аналогично ограничить диапазон до 850..930 MHz.

Для других усилителей доступна таблица DTS из троек:

```dts
/* Выход модуля, мощность чипа, регистр OCP; пример, не универсальная калибровка. */
semtech,tx-power-table = <10 (-9) 0x38>,
                         <20 1 0x38>,
                         <30 11 0x38>;
```

Принимаются только перечисленные выходные мощности. Есть аппаратные свойства
PA duty cycle, hpMax, ramp, regulator mode, TCXO voltage/startup и переключения
RF. `semtech,dio2-rf-switch` включает автоматическое управление через DIO2;
его нельзя сочетать с внешними RXEN/TXEN GPIO. DIO3 используется для TCXO.

Режим регулятора принимает только документированные 0/1. Старое значение
`0x11` из userspace-плагина не перенесено. Инициализация выполняет калибровки,
настройку LDRO, workaround для BW500/IQ/TX clamp, чтение sync word обратно и
проверку DeviceErrors. Наличие устройства в `/dev` ещё не подтверждает SPI/RF:
радио впервые запускается при успешном `SET_CONFIG`.

## ABI версии 1

Полное описание структур — `include/uapi/linux/sx1262.h`. Целые числа native
endian, указателей в ABI нет; размеры и выравнивание одинаковы на ILP32/LP64.
Зарезервированные поля обнулить. Один процесс открывает устройство эксклюзивно;
чтение и отправка из разных потоков одного процесса поддерживаются.

1. `open(O_RDWR)` или `open(O_RDWR | O_NONBLOCK)`.
2. `GET_CONFIG`, изменение нужных полей, `SET_CONFIG`. При открытии RX включён
   как желаемый режим; успешная настройка запускает непрерывный приём.
3. `read()` / `poll()` для событий, `write()` / `TX_BATCH` для отправки.

| Операция | Семантика |
| --- | --- |
| `write(fd, payload, 1..255)` | Принять один фрейм в очередь; возврат длины **не означает TX_DONE** |
| `TX_BATCH` | Принять 1..8 фреймов и 64-битный cookie как одну заявку |
| `read()` | Одна структура `sx1262_event`, ровно 296 байт |
| `GET_CONFIG` / `SET_CONFIG` | LoRa PHY и watchdog |
| `SET_RX` | `u32` 0/1: standby или непрерывный RX |
| `GET_STATS` | Счётчики, online, last_error, количество ожидающих/активных заявок |
| `RESET` | Аппаратный reset с повторным применением конфигурации |

Конфигурация: Hz, BW, SF5..12, CR denominator 5..8, мощность выхода модуля,
преамбула, sync word, CRC, IQ inversion, explicit/implicit header и фиксированная
длина для implicit. LDRO: auto/off/on. Принимаются как старые округлённые названия
узких BW (7800, 10400, …), так и значения 7812, 10417, 15625, 20833, 41667;
airtime рассчитывается по точным делителям. Недопустимые комбинации и airtime
свыше 240 секунд на максимальный payload отклоняются.

При ожидающем/активном TX изменение конфигурации, RX и RESET возвращает `EBUSY`.
Неудачное применение валидной конфигурации оставляет её желаемой, радио offline;
watchdog повторяет инициализацию. При смене конфигурации старые RX-записи остаются
в очереди — приложение должно учитывать это или предварительно её прочитать.

RX-событие содержит исходный payload, RSSI в половинах dBm, SNR в четвертях dB
и программную отметку `CLOCK_BOOTTIME`. Это время наблюдения драйвером, не
аппаратное время окончания пакета. Ошибочные CRC/header фреймы учитываются
в статистике и не выдаются приложению.

TX-событие содержит cookie (для `write()` — 0), `status = 0` либо отрицательный
errno и `frames_sent` — число фреймов с подтверждённым TX_DONE. После ошибки
остаток группы не передаётся; автоматического повтора нет. Если передача
успела закончиться, но возврат в RX завершился ошибкой, возможны ненулевой
status и `frames_sent == count`. TX_DONE не подтверждает доставку получателю.

## Очереди и следующие подряд фреймы

Общая ordered workqueue сериализует **все** передачи этого драйвера, включая
радио на разных SPI-контроллерах. Максимум 64 активных/ожидающих заявки.
Группа удерживает очередь до завершения всех своих фреймов. Между фреймами
нет случайного backoff или возврата в RX; есть необходимое время SPI/GPIO и
планирования. Для пары фрагментов использовать один `TX_BATCH`: два отдельных
`write()` не резервируют место от вклинивания другого отправителя.

На радио резервируется максимум 32 TX-результата, считая ещё не завершённые
заявки. Они не вытесняются RX. **TX-результаты необходимо читать**, иначе новые
отправки блокируются; с `O_NONBLOCK` возвращают `EAGAIN`. `POLLOUT` означает
наличие места для заявки, не свободный эфир. Приложение может одновременно
читать события и ставить новые заявки в очередь.

На радио есть отдельная RX-очередь из 128 записей. При переполнении отбрасывается
новый пакет и увеличивается `rx_dropped`. `read()` сначала выдаёт TX-результаты,
поэтому записи разных типов не обязательно упорядочены по времени. Маленький
буфер возвращает `EMSGSIZE`; `EFAULT` не удаляет событие из очереди.

После RX_DONE радио остаётся в continuous RX. Обработчик подтверждает снимок
IRQ, быстро копирует payload/метаданные и повторно проверяет флаги. SPI-шина
не удерживается на время передачи в эфире. Соседние модули продолжают принимать,
хотя близкий мощный передатчик физически может подавлять их приём.

Очередь Linux защищает от задержек приложения, но SX1262 не имеет полноценной
очереди принятых пакетов. Задержка IRQ/SPI/I²C больше интервала между пакетами
может привести к потере или перезаписи аппаратных данных. Это особенно важно
на SF5/BW500 и при восьми модулях. Такие потери не всегда наблюдаемы счётчиком
`rx_dropped`; измерять их нужно по sequence number в тестовом payload.

## Watchdog и жизненный цикл

Watchdog каждые 100 ms проверяет IRQ по SPI, чтобы подобрать потерянные события.
Успешный ответ SPI не считается доказательством работоспособности IRQ.
Таймер тишины отсчитывается от обработанного собственного IRQ, а не от
активности соседей на общей линии и не от поллинга.

По умолчанию после 60 секунд без IRQ выполняется мягкий перезапуск RX;
после двух последовательных watchdog recovery — reset и полная инициализация.
Настройки: `silence_timeout_ms` (0 выключает защиту тишины) и `hard_reset_after`.
После восстановления таймер начинается заново. Незавершённый приём защищён
отдельно, даже при выключенном таймере тишины:

- После PREAMBLE_DETECTED ждём HEADER_VALID не дольше
  `max(100 ms, 1.5 × длительность преамбулы + 25 ms)`.
- После HEADER_VALID ждём завершения кадра не дольше
  `max(100 ms, 1.5 × длительность payload максимальной длины + 25 ms)`.
  Время преамбулы сюда не входит; LDRO учитывается.
- Повторные IRQ той же стадии не продлевают дедлайн. RX_DONE, ошибки CRC/header
  и аппаратный timeout снимают его. Перед восстановлением читается IRQ-регистр,
  чтобы обработать завершение, если был потерян только сигнал прерывания.

Для SF7/BW125, преамбулы 25, CR4/5 и CRC таймауты составляют 100 ms и 607 ms
вместо прежних 1836 ms на каждую стадию. Watchdog приближает следующий запуск
к RX-дедлайну, когда до него меньше 100 ms; фактический запуск зависит от
планировщика, точности jiffies и задержек SPI/I²C.

В implicit mode HEADER_VALID может отсутствовать: после преамбулы отводится
время на весь кадр заданной фиксированной длины с тем же запасом. Если HEADER_VALID
всё же пришёл, начинается таймаут оставшейся части. В standby таймер тишины
не применяется.

TX имеет аппаратный таймер, программный deadline и опрос IRQ каждые 20 ms
при отсутствии завершения. Таймаут или ошибка обмена приводят к восстановлению
конкретного радио. BUSY ждём не дольше 200 ms на операцию. Ошибка в IRQ-потоке
удерживает неисправный модуль в reset, чтобы освободить DIO1, и откладывает
повторную инициализацию. Offline-радио повторяет её примерно раз в секунду.

`close()` останавливает радио и отменяет остаток заявок этой сессии. Следующее
открытие не получает её TX/RX-события. `remove()` будит ожидающие операции;
старые fd возвращают `ENODEV` после чтения уже накопленных событий. Объект живёт
до освобождения fd/заявок, но после remove аппаратных обращений нет.

Если общая линия физически закорочена в высокий уровень, reset радио может
не помочь. Драйвер не отключает общий IRQ из-за одной ошибки; резервный опрос
остаётся доступен, но не гарантирует приём плотного потока при неисправной линии.

## Проверки и испытания

```sh
make test
make tools CROSS_COMPILE=/path/to/arm-buildroot-linux-gnueabihf-
```

Пример на целевой машине (оба конца должны иметь одинаковые PHY-настройки):

```sh
# RX до остановки процесса
./sx1262-test /dev/sx12620 868000000 125000 7 14
# На другом устройстве: два последовательных raw-фрейма
./sx1262-test /dev/sx12621 868000000 125000 7 14 01020304 aabbccdd
```

В этой рабочей среде проверены сборка ARM/Linux 6.12.3 с `W=1`, сборка и
установка через пакет Buildroot, checkpatch, ABI на ARM и x86-64, airtime/LDRO
и валидация конфигурации. ARM-тесты также запускались статически под qemu-user.
Пример DTS прошёл cpp/dtc. Полная проверка dt-schema требует отдельной установки
пакета dtschema. Сборка не заменяет проверки аппаратного обмена.

До эксплуатации выполнить сценарии `tests/hardware.md`, особенно плотные
255-байтовые фреймы, совпадающие IRQ, зависание одного из восьми модулей и
калибровку выходной мощности E22/внешнего усилителя. RF и аппаратная работа
на этой машине не проверялись.

Регистры и последовательности сверялись с официальным драйвером Semtech:
https://github.com/Lora-net/sx126x_driver . Код Linux-драйвера самостоятельный;
профиль E22 основан на настройках соседнего rsReticulum-sx1262.
